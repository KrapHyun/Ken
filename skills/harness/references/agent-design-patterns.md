# Agent Design Patterns for Current Codex

현재 Codex에서는 메인 에이전트가 중심이 되고, 위임이 허용된 경우에만
서브에이전트를 보조적으로 사용한다. 직접 팀 API나 에이전트 간 직접 메시징은
기본 가정으로 두지 않는다.

## 실행 모드

### 1. 문서 설계 모드

```text
[메인] -> 역할 문서 작성 -> 스킬 작성 -> 플러그인 패키징
```

적합한 경우:

- 사용자가 실제 delegation을 요청하지 않았다
- 우선 설계 자산을 남기는 것이 중요하다
- 현재 런타임 제약을 넘는 기능을 문서화 수준으로만 정리해야 한다

### 2. 병렬 위임 모드

```text
[메인]
  ├─ spawn_agent(A)
  ├─ spawn_agent(B)
  └─ 결과 통합
```

적합한 경우:

- 사용자가 명시적으로 서브에이전트, 병렬 처리, delegation을 요청했다
- 하위 작업이 서로 독립적이다
- 산출물을 파일이나 요약으로 다시 합칠 수 있다

### 3. 생성-검수 루프

```text
[메인] -> 생성자 -> 검수자 -> send_input 또는 재실행 -> 최종본
```

적합한 경우:

- 초안 품질이 중요하다
- PASS/FIX/REDO 같은 구조화된 판정이 가능하다

## 패턴 선택표

| 패턴 | 적합한 경우 | Codex 권장 형태 |
|------|-------------|-----------------|
| 파이프라인 | 순차 의존 단계가 강함 | 메인 주도 순차 실행 |
| 팬아웃/팬인 | 같은 입력을 여러 관점으로 분석 | 명시적 병렬 요청이 있을 때만 다중 spawn |
| 전문가 풀 | 입력에 따라 전문가가 달라짐 | 메인이 먼저 분류하고 필요한 역할만 선택 |
| 생성-검증 | 초안과 리뷰가 반복됨 | 생성자 + 리뷰어 루프 |
| 감독자 | 작업 배치 재분배 필요 | 메인이 상태 파일로 진행률 관리 |
| 계층적 위임 | 복잡한 위계 구조 | 가능한 한 2단계 이하로 평탄화 |

## 역할 분리 기준

| 기준 | 분리하는 편이 좋다 | 합치는 편이 좋다 |
|------|--------------------|------------------|
| 전문성 | 판단 기준이 분명히 다름 | 한 맥락에서 한 번에 처리 가능 |
| 병렬성 | 동시에 실행해도 충돌이 적음 | 순차 의존이 강함 |
| 컨텍스트 | 한 역할에 넣기엔 문맥이 너무 넓음 | 한 사람이 보는 편이 오류가 적음 |
| 재사용성 | 이후 다른 프로젝트에도 반복될 역할 | 이번 작업에서만 일시적으로 필요 |

## 현재 Codex 역할 선택

| 역할 | 적합한 작업 |
|------|-------------|
| `default` | 조사, 요약, 분석, 설계 |
| `explorer` | 읽기 중심 탐색과 코드 분석 |
| `worker` | 파일 수정, 구현, 테스트 수정 |

주의:

- `explorer`에게 수정 작업을 맡기지 않는다.
- QA가 수정까지 포함하면 `worker`가 더 맞다.
- 특별한 이유가 없으면 모델 강제보다 현재 세션 기본값 상속을 우선한다.

## 역할 문서 구조

```markdown
---
name: reviewer
description: "무엇을 검토하는 역할인지 짧게 설명"
---

# Reviewer

## 핵심 역할
## 작업 원칙
## 입력/출력 프로토콜
## 에러 핸들링
## 협업 규칙
```

협업 규칙에는 다음을 명시한다.

- 어떤 파일을 읽는가
- 어떤 파일을 쓰는가
- 메인 오케스트레이터에게 어떤 형식으로 상태를 보고하는가

## 파일 기반 협업

직접 메시징보다 파일 기반 계약을 기본으로 둔다.

권장 구조:

```text
_workspace/
├── 00_input/
├── 10_research/
├── 20_build/
├── 30_review/
└── status/
```

파일명 규칙 예:

- `01_analyst_requirements.md`
- `20_builder_patch_plan.md`
- `30_qa_review.md`

## 안티패턴

- 지원되지 않는 팀 API를 전제로 설계
- `.codex/agents/*.md`를 자동 실행 타입이라고 가정
- 위임 요청이 없는데 기본 실행을 무조건 spawn 기반으로 설계
- 병렬 이득이 없는 작은 작업까지 모두 서브에이전트화
- 데이터 전달 계약 없이 막연한 역할 설명만 작성
